# 一、项目愿景、定位与核心价值

## 1.1 项目定位

AI Tileset Studio 是一个以 **AI 辅助视觉创作、确定性地图图块编译、质量检测及素材包管理**为核心的游戏地图素材生产平台。

首期专门面向 RPG Maker MZ。用户通过自然语言、可选参考图片和少量易理解的创作参数，生成能够直接用于实际地图开发的标准素材，而不仅是看起来好看的场景图。

完整的生产流程为：

    用户创作意图 / 参考图 / 可选辅助提示词
                    ↓
            平台创作配方与主 Prompt
                    ↓
              AI 视觉资产生成
                    ↓
           纹理、边缘和动画处理
                    ↓
            引擎无关图块中间结果
                    ↓
           MZ 编译片段 + Layout Plan
                    ↓
             A1/A2 最终素材包
                    ↓
          结构质检 + 动画/拼接预览
                    ↓
          下载并在原生 MZ 中注册使用

用户无须手动整理几十种子图块、理解固定的图集坐标，或者自己裁切 PNG 才能使用 Autotile。

## 1.2 核心产品价值

**视觉质量：** 产生具备统一像素风格、自然纹理和适当动态效果的美术素材；关注大面积铺设与实际场景观感，不止关注一张孤立图片。

**工程正确性：** 使用程序保证目标引擎的 Autotile 子块规则、帧结构、槽位、文件格式和基本连接关系；图像生成模型不负责最终图集排版。

**稳定交付：** 可以选择候选、调整源组件、质量检测、重新编译、保留旧版本和导出可使用的素材包；失败不损坏之前的成功结果。

**长期可扩展性：** 核心材质、连接、动画语义与 MZ 的格式规则分开。未来增加其他地形、多帧增强运行时、不同引擎和智能笔刷，应尽量在已有能力上扩展。

## 1.3 长期产品方向

**第一阶段：AI 地图素材生产平台。** 聚焦素材创作、标准化、原生 Autotile / Animated Autotile、素材包管理、预览、质量和导出。

**第二阶段：智能笔刷地图编辑平台。** 在稳定材质体系上增加道路连接、河道宽度与深度、山体层级、森林密度等参数化地图绘制。

之后可能上线 SaaS、引入用户、第三方认证、计量、账本、支付和审计；也可能提供 Shader、水流、树木独立摇摆等动态环境能力。但这些不是首期承诺。

# 二、首期 V1.0 范围与明确排除项

## 2.1 最小完整交付单元

V1.0 不以“独立生成一张草地”和“独立生成一张水面”为终点，而以以下**配套素材包**为单位：

**一套共享美术风格、可以在同一张原生 MZ 地图上配合使用的 A2 草地 + A1 动态水面 + 固定草地—水面岸线关系。**

这一套内容必须既能人工导入源素材编译，也能由 AI 创作流程产生。文字创作路径与参考图创作路径都应最终产生一套完整、可交付的配套素材，而不是分别只生成草地或只生成水面。

| 能力 | V1.0 要求 |
|---|---|
| 游戏引擎 | 原生 RPG Maker MZ |
| 风格 | 高质量 2D 像素风 |
| 基础 Tile 尺寸 | 正式支持 48×48 |
| 地形 | 草地、普通动态水面，以及二者间一种固定岸线配方 |
| Autotile | 静态草地正确自动拼接 |
| Animated Autotile | 原生水面三源帧自动拼接并播放 |
| 图集 | 对 A2 普通地面和 A1 普通水面经验证子集的编译、组合、导出 |
| 生成方式 | 平台内置主 Prompt；用户可选辅助 Prompt；文字、参考图和人工基础素材导入 |
| 模型策略 | 普通用户不选择模型；后端集中配置默认模型 |
| 素材处理 | 合格输入验证、纹理/边缘/遮罩/动画组件处理 |
| 预览 | 创作预览；从实际导出图集读取并播放的交付预览 |
| 质量 | 工程硬校验、基础视觉风险检测、可定位的修复流程 |
| 数据 | 项目保存、素材 revision、依赖、构建历史与失败保护 |
| 素材包 | 稳定槽位、退役语义、Manifest、说明与下载 |
| 真实兼容 | 原生 MZ 编辑器绘制与游戏运行验收 |
| 额外 MZ 插件 | 不需要 |

**浏览器内直接预览水面动态效果是 V1.0 的正式功能。** 用户可以在工作台查看水面波纹与拼接后的池塘，不需要每次都先把 PNG 下载到 MZ 里才能观察动画。该预览仍不能替代 MZ 实机验收。

## 2.2 非目标与明确排除

V1.0 **不做**完整地图编辑器、参数化智能笔刷、自动地图布局、建筑/角色/怪兽资源、海洋/深海联动、瀑布、岩浆、崖壁以及 A3/A4/A5/B-E 的全面编译。

不做 MZ 专用多帧插件、任意 N 帧运行时、Shader 编辑、风场、树木摇摆、复杂粒子特效。未来可以扩展，但不能拿“支持多帧”作为首期默认承诺。

不做账号注册、Google 登录、微信/支付宝/Stripe、Credits 充值、订阅、计费账本、收费审计、素材商城、多人协作、Redis/BullMQ 或线上 SaaS 部署。不应为了这些后续需求提前增加一套复杂商业化基础设施。

不承诺任意草地和任意水面自动混搭；首期仅保证明确定义的**每套固定组合内部**的岸线过渡正确。

不承诺向已有用户项目自动写入或覆盖 Tilesets.json、地图数据及其他图集。用户需要按说明在 MZ 数据库设置对应图片、模式和通行属性。

# 三、MZ Target Profile：原生引擎兼容契约

## 3.1 为什么首期必须收窄到 Target Profile

A1 和 A2 不是“只要 PNG 尺寸相同就能随意填充”的图集。A1 的水面、特殊海洋和瀑布有不同规则，A2 又有普通地面、装饰地面与地图模式行为差别。

因此“支持 A1/A2”不足以作为验收。首期必须建立唯一、经过实机验证的：

**MZ Native Ground & Water Profile v1**

所有编译、Pack 规划、交付预览、安装指南、测试用例和错误提示，都必须引用同一份 Profile，而不是分别硬编码一套自己的规则。

## 3.2 首期 Profile 基线

| 项目 | 选择与验证责任 |
|---|---|
| 引擎/运行时 | 未修改的 RPG Maker MZ；V0.0 固定实际版本及核心脚本版本 |
| 地图编辑模式 | Area Type；首期不支持世界地图专用绘制行为 |
| Tile 尺寸 | 48×48（主动限定的产品子集，不表示 MZ 只能用此尺寸） |
| 图集 | 48px 基线下 A1、A2 均按 768×576 PNG 格式 |
| 静态地面 | A2 普通地面中经过验证的指定槽位 |
| 动态水面 | A1 Block D 普通水面中经过验证的指定槽位 |
| 可分配容量 | V0.0 明确允许槽位集合、每类数量、保留及容量不足行为 |
| 岸线 | 一种在原生编辑器可用的固定叠加/烘焙配方，V0.0 实验后冻结 |
| 动画源帧 | 三个源状态，播放序列 0 → 1 → 2 → 1 → 循环 |
| 动画时基 | 以已固定的运行时 Tilemap.update 规则为准；公开实现每 30 次更新推进一状态 |
| 地形属性 | 提供经过验证的推荐通行配置；Counter 不启用，Bush 等特性无额外保证 |
| 透明叠加 | 只支持验证过的策略；不接受任意图层自由组合 |
| 排除项 | 深海/海洋联动、瀑布、任意 A1 子类、桌子、任意槽位重排及所有未声明功能 |
| 插件 | Native Profile 不依赖专用 MZ 插件 |

“暂定槽位”与“实测冻结槽位”必须在文档状态中区分。V0.0 输出精确坐标、形态列表、容量与试验记录后才正式冻结 Profile。

## 3.3 水面动画：源帧、播放序列和时间基准

MZ 原生普通水面不是简单的三帧 0→1→2→0 等间隔循环，而是以 **0→1→2→1** 选择三个素材源状态。在已公开的 Tilemap 逻辑中，动画计数每经过 30 次 update 推进一个状态。具体适用性必须以选定引擎版本实测为准。

因此平台预览不允许用“浏览器每刷新一次就跳到下一张图”的方式冒充 MZ 真实动画。它应依据 Profile 的时间与顺序规则进行播放、暂停、逐状态检查。

这种往返式循环更适合柔和的水面起伏、波纹和反光；**不承诺能够自然表达需要持续单向流动的河流或瀑布**。

内部通用 Animation Clip 仍允许描述其他帧数、步骤时长及循环方式，但 Native Compiler 遇到不兼容的 N 帧素材必须显式提示或拒绝，不得悄悄删帧而宣称无损兼容。

## 3.4 实机验收必须区分三种正确性

1. **渲染正确：** 已知 Tile ID、Autotile 形状和动画状态，对应正确的子图块和像素。
2. **编辑器绘制正确：** 用户在正常 MZ 地图编辑器里使用画笔创建水池、长边、拐角、孔洞等，编辑器自动选图和图层行为正确。
3. **游戏使用正确：** 未修改的 MZ Runtime 中动画正常、图层和推荐通行配置符合预期。

只验证第一项不能推出第二项。尤其需要保留一份**在编辑器中实际手绘产生**的测试地图，用于后续 Pack 更新兼容性验收，不能每次自动重造一张测试地图。

# 四、用户产品工作流与界面要求

## 4.1 创建项目及风格

用户打开本地 Web Studio，创建素材项目，选定目标引擎、风格及素材任务。首期 Target Profile 默认固定，UI 不需要复杂的引擎选项。

Style Profile 约束颜色、像素逻辑密度、光照/阴影、轮廓与风格一致性，可以在同一配套材质间复用。

## 4.2 提供创作需求

用户可以：

- 直接选择“生成草地与动态水面”固定生产任务。
- 可选输入额外美术偏好，如“湖水更清澈、草地偏明亮、水波纹更柔和”。
- 可选上传参考图片，表达配色、风格或某一组件的视觉目标。
- 导入自有合格的基础纹理，绕开 AI 生成进入确定性流程。

**不能强制用户自己写一段完整 Prompt，才能生成素材。**

## 4.3 候选生成和组件编辑

平台产生候选源素材并标注对应任务和版本。用户可以选择候选、替换单个源纹理、针对边缘或水面视觉组件重新生成，再进入配方处理。

局部修改不是让图像模型凭空保证“其他地方一像素不变”。需要保留的岸线或草地由平台使用遮罩、裁切及合成操作保护；改变组件后重建受影响的依赖和图集。

## 4.4 编译、QA 和两类预览

**创作预览：** 可以看原始纹理、遮罩、组件和水面源动画的效果，方便筛选。

**交付预览：** 必须读取本次实际构建的 PNG、Manifest 和 Profile，由与目标形态一致的图块规则重新构建池塘/草地场景，直接在线播放波纹。包含孤立格、直边、内外角、孔洞、窄通道、大片区域等典型形状。提供暂停/播放、状态切换与质量问题定位的实用能力。

交付预览来自最终构建文件，但仍需独立图块样例和 MZ 实机测试，防止预览器与编译器共享一套错误坐标表却“自证正确”。

## 4.5 导出与 MZ 使用

交付至少包含 A1/A2 标准 PNG、Build Manifest、槽位映射、安装说明、基本预览和必要的 MZ 示例工程/验收说明。

用户把图集放进 MZ 项目的 img/tilesets，打开数据库创建或配置 Tileset 项目、选择 Area Type 与对应 A1/A2 图片，再设置所需通行属性，然后使用原生画笔绘图。

“可直接用于 MZ”意味着无需手工重排图块、无需平台专用插件，**不是**完全不用在数据库注册资源。

# 五、系统内置 Prompt Strategy（关键正式需求）

## 5.1 主 Prompt 与辅助 Prompt 的权责

**平台维护的主 Prompt 是生成请求的主体；用户的 Prompt 是完全可选的辅助偏好。**

必须内置版本化 Prompt 模板，覆盖草地纹理、普通动态水面的共享基础纹理/波纹元素、固定岸线、参考图编辑等正式任务。模型更换时可以适配不同模型的输入风格，但系统规范始终来自平台。

主 Prompt 至少表达：

- 目标是 RPG 游戏中可重复铺设的地形素材，不是带透视的场景插画。
- 当前具体材质和组件的角色：地面、表面、岸线、波纹或边缘。
- 目标像素风的密度、线条、颜色、光照和一致性要求。
- 地形大面积重复、连续纹理、边缘/角落与透明区域的期望。
- 多帧动画共享几何、岸线稳定、循环连贯等约束。
- 需要排除的无关物体、文字、水印、非期望镜头透视和装饰。
- 当前任务期望产出的**源组件**形式，而不是让模型自行拼 A1/A2。

上述内容应以类型化任务模板和结构化输入组合，而非把一段固定的万能长 Prompt 无条件用于所有任务。

## 5.2 用户辅助提示词

用户 UI 可显示“补充描述（可选）”，主要用于颜色、季节、氛围、质地或动画的视觉强弱。留空也应正常生成默认素材。

用户补充不能取消系统结构规范、改变输出素材角色、要求平台首期不支持的引擎类型或覆盖重要像素处理限制。冲突请求可提示用户修改，或按明确规则仅取有效美术偏好。

**仅把用户文字拼在前面/后面，不能在工程上保证模型绝不违约。** 后端应限制结构化任务的可变范围，生成后仍必须通过输入规范和确定性 QA。

## 5.3 Prompt Composer 与模型 API 适配

后端 AI 层形成如下概念结构：

    Platform Main Prompt (versioned)
            + Task Template (versioned)
            + Target / Style Profile + structured parameters
            + Reference Asset Context
            + Optional User Supplemental Prompt
            → Provider Adapter → Actual Model Input

有的图片模型没有单独的 system 消息通道，此时 Adapter 应把各部分组合为模型允许的字段，不能虚构 API 提供了 system role。普通用户不需要看到模板全文或供应商名称，但工程记录必须可追踪。

## 5.4 Prompt 版本冻结与迭代

每个生成任务创建时冻结：主/任务 Prompt 模板版本、用户辅助提示词、结构化参数、参考资产 revision、实际模型、Provider 及相关配置版本。Worker 不得在排队期间重新读取新默认 Prompt 或新模型造成任务语义漂移。

将 Prompt 模板纳入 Git 管理，变更需要测试和可审查记录。通过固定评测集比较主模板更新的质量、成本和失败情况，避免只优化几个演示案例。

# 六、AI 模型接入、WaveSpeed 和默认模型策略

## 6.1 首期 Provider

首期接入 **WaveSpeed**，优先参考其[官方 JavaScript SDK](https://wavespeed.ai/docs/javascript-sdk)，npm 包名 wavespeed；SDK 仅在 NestJS 后端的 Provider Adapter 内使用。客户端不持有 API Key，也不直接请求第三方模型。

AI Gateway 为业务提供“生成源素材”“基于参考图编辑”“必要时视觉分析”等任务能力。模型特有参数由 Adapter 与 Model Registry 管理，不强行让每个模型共用不兼容的参数。

## 6.2 隐藏普通用户的模型选择

V1.0 前端不展示一堆模型名称让用户选择。平台为 Image Generate、Image Edit 等能力集中配置默认模型，并仅暴露用户能理解的“生成、修改、重新生成”操作。

可以把某个 GPT Image 2.5 的 WaveSpeed 端点作为候选，但最终默认模型须在 V0.2 用真实账号、实际素材效果、延迟、失败率、每套可用素材成本和商用使用条款评估。**候选模型存在不等于已验证可用。**

Model Registry 首期可以是服务端的类型化静态配置；不需要管理后台、动态路由或多个已实现 Provider。通过 Mock 验证抽象可替换即可。

## 6.3 AI Gateway 的职责边界

Provider Adapter 负责：认证/上传、提交、查询、供应商错误映射和结果规范化；如官方 SDK 不能独立获取任务 ID，可在该 Adapter 内用官方 REST 完成受控补充。

平台任务执行器负责：逻辑任务生命周期、PostgreSQL 持久化、恢复策略、重试/取消和项目快照版本检查。

通用资产归档负责：下载远端结果、校验实际文件、计算哈希并保存到本地不可变目录。

这些职责不应随着未来增加 Provider 而在每个 Provider Adapter 中重复一份数据库状态机。

## 6.4 未来模型升级

更换默认模型只需更新中心配置并做必要能力回归；**仅影响新建任务**。旧任务、历史素材和构建记录保留原本模型/Prompt 信息。

真实模型接入前必须用 Mock 走通任务恢复；真实模型测试必须限制并发、调用次数和可接受预算，费用估算与真实返回费用分别记录，不能声称拥有尚未实现的精确硬额度系统。

# 七、异步任务、故障恢复与取消语义

## 7.1 任务状态模型

完整逻辑任务至少能够区分：

    CREATED / QUEUED
          ↓
    SUBMITTING
          ↓
    REMOTE_RUNNING (external prediction ID known)
          ↓
    FETCHING_RESULT
          ↓
    VALIDATING_AND_INGESTING
          ↓
    COMPLETED (local artifact durable)

以及 SUBMISSION_UNKNOWN、FAILED、CANCEL_REQUESTED、CANCELLED_LOCAL 等真实异常或控制状态。名字可在契约中确定，但语义不可混淆。

**只有本地结果校验并归档成功才算平台任务成功。**供应商返回“成功”不代表用户资产已经安全保存。

## 7.2 四类必须分别处理的异常

| 场景 | 必须保证 |
|---|---|
| 已持久化外部 ID，之后断线或重启 | 查询原任务，不能重新生成 |
| 提交后连接中断但不知道外部 ID | 记录提交结果未知，不盲目重试；通过可用的供应商记录核对 |
| 远端已经完成，下载/校验/保存失败 | 只重试归档，不再次购买一份生成 |
| 用户取消、回调重复或旧任务晚返回 | 分清本地停止与远端取消；幂等处理重复结果；旧结果不覆盖当前项目 |

仅靠本地任务 ID 或幂等键，不能保证供应商没有重复创建任务。没有外部保证时，应该采用保守的恢复与人工诊断策略。

## 7.3 任务测试前置

在 **V0.1 / 十步计划步骤 06**，先使用 Mock Provider 完成基本持久化、未知提交、查询恢复、结果归档、取消和竞态测试。**步骤 08 不应首次发明任务状态机**，它应验证 WaveSpeed 是否满足既定 Provider 契约并开展预算受控的真实生成/编辑连通测试。

生成结果和上传文件的第三方临时链接不能当作长期存储，必须及时归档到本地或未来的对象存储。

# 八、引擎无关素材模型、像素契约与版本依赖

## 8.1 三层素材表达

**第一层 — 创作源与配方：** 保存原始纹理、参考图、Style Profile、AI 调用信息、固定岸线遮罩、过渡配方及动画组件。

**第二层 — Tile IR：** 保存逻辑图块、连接类型、边缘/内外角、像素区域、透明合成、动画源帧及播放语义，与 MZ Tile ID 无关。

**第三层 — Target Build：** 保存已编译片段、布局、A1/A2 实际图集、Manifest、哈希、配置建议及质量状态。

关键概念可包括 Material、Surface、Transition、Autotile Definition、Animation Clip、Style Profile、Terrain Semantics、Target Profile、Pack 和 Build Record，但**不要求每一个名词对应单独服务、包或表**。

## 8.2 Pixel Processing Contract

V0.0 明确并通过诊断样例验证：

| 项目 | 约束方向 |
|---|---|
| 工作像素 | RGBA8，统一处理透明度表达 |
| 色彩 | sRGB 为首期处理/输出基线，定义外部 ICC/色彩转换策略 |
| 坐标 | 整数像素坐标，明确 crop 边界、越界和取整策略 |
| Alpha | 明确半透明、预乘或非预乘表示、合成和透明像素规范 |
| 像素密度 | 美术逻辑像素密度与 48×48 最终 Tile 分开 |
| 缩放 | 像素画整数放大应使用合适的最近邻方案；其他重采样显式决定 |
| 调色 | 同一素材套系及动画各帧共享约束，不无意漂移 |
| 动画几何 | 固定岸线/遮罩，明确可变化的内部波纹区域 |
| 输入不合格 | 拒绝或显式转换与重新验证，不默默修坏源图 |

Sharp 可以用作解码、编码、裁切和一般图像处理，但不能无条件采用其默认缩放参数当作像素风正确性保证。高分辨率 AI 生成图压缩成低逻辑像素图是独立的质量难题，不是一条 resize 就解决。

## 8.3 素材输入状态

每份素材须经过：

    RAW_SOURCE → VALIDATED_SOURCE → COMPILABLE_RECIPE → BUILT_ARTIFACT

文件上传成功不等于已验证，不合格输入应给出尺寸/像素密度/透明度/组件角色或几何错误提示。

## 8.4 固定岸线与版本引用

Transition 必须绑定草地、水面及遮罩的**具体不可变版本**或内容哈希，并记录边界拥有者、静态/动画区域和依赖的参数版本。

例如：

    Pack Build K = grass@3 + water@1 + shoreMask@2 + recipe@5

后来发布 grass@4，**不会让已有 Build K 自动失效**。只有当前工作项目切换使用 grass@4 后，相关“当前配套岸线”才进入待重建状态；历史结果仍可以原配置复现。

清楚区分“有新版本”“当前依赖需要重新编译”“某历史产物验证失败”。不要用一个泛化的 stale 标志表达三种不同事实。

## 8.5 地形视觉与通行语义

岸边的草色像素不等于那部分可以行走。首期遵循 MZ 自身的图块/方向通行设置，而非开发像素级碰撞；提供已验证配置与说明即可。

# 九、编译器、布局、素材包与槽位生命周期

## 9.1 三个严格分工的动作

**MZ Compiler：** 输入合法 Tile IR 和 Target Profile，输出符合 MZ 子块/连接/源帧规则的 **Compiled Fragment** 及放置约束。它不决定素材包中的最终空闲槽位。

**Pack Assembly：** 根据逻辑素材身份、当前稳定绑定、Profile 支持槽位和容量，唯一负责生成 **Layout Plan**。已有绑定不能因更新或增加素材而被静默移动。

**Final Atlas Renderer：** 仅依据已验证 Fragment + Layout Plan 写入完整 A1/A2 PNG，不重做布局决策，也不重新定义 MZ 子图块规则。

可以在同一 TypeScript Package 内实现三种职责，不因此要求新增三个微服务。步骤 04 可沿用步骤 01 的**固定诊断图集布局**测试 Fragment，不能因此建立第二个生产用槽位分配器。

## 9.2 Pack、Manifest 与导出

Pack 是同一 MZ Tileset 中可长期维护的逻辑素材集合，而不是单个 PNG。V1.0 采取固定、经验证的槽位集合，容量不足明确报错；不做任意第三方 A1/A2 混合图集编辑器。

Build Manifest 至少记录 Pack/构建版本、Target Profile、逻辑素材→目标槽位映射、源/配方 revision、Compiler/布局版本、输出文件哈希、依赖关系、推荐数据库设置和验证状态。

导出格式包括 A1/A2 PNG、机器可读 Manifest、预览/说明及必要的 MZ 示例工程。用户手动注册目标 Tileset，不覆盖已有项目数据。

## 9.3 槽位分配和退役规则

| 状态 | 是否可自动用于新素材 | 历史兼容 |
|---|---|---|
| NEVER_USED | 是 | 无既有绑定 |
| ACTIVE | 否 | 保留逻辑素材身份与槽位 |
| RETIRED | **否** | 默认保留最后的兼容画面与绑定历史 |

“从素材库退役”不等于“清空图像”或“把槽位分给另一种草”。真正清空或复用曾使用的槽位属于可能破坏旧地图的操作，需明确标为破坏性变更；V1.0 不承担旧地图自动 Tile ID 迁移。

## 9.4 实际兼容验收

不只比较两个 Manifest 的槽位编号，还要拿**之前正常编辑器画好的 MZ 测试地图**实际替换素材包，确认旧地图中的草地、水面和岸线显示仍满足声明。新增/更新、退役/保留、容量不足、冲突、构建失败都应有确定性测试。

# 十、项目持久化、构建原子发布与备份恢复

## 10.1 本地存储架构

首期 PostgreSQL 保存项目、任务、版本、配方、依赖、构建及 Pack 元数据；本地文件系统保存原始资产、派生图像和最终图集。通过 Prisma 访问数据库，文件存储通过独立 Asset Storage 接口。

项目/资产/任务必须具备稳定 ID，未来可关联用户和 Workspace，但 V1.0 不开发权限或支付模块。

## 10.2 不可变构建与发布协议

源资产 revision 和正式构建结果尽量不可变。新构建使用新目录，不覆盖上一次成功 PNG。最小发布协议：

    编译到临时/暂存位置
        → 校验完整文件、依赖与哈希
        → 固化为不可变资产与构建目录
        → PostgreSQL 短事务登记文件引用和构建元信息
        → 用项目/Pack 预期版本检查切换当前成功构建指针

数据库失败可产生待清理的孤立文件，不能出现数据库显示构建成功但对应文件缺失。不得把网络等待或大量像素处理包在长数据库事务里。

两个构建反向完成时旧版本只能进入历史，不能自动切回当前；同 Pack 的槽位规划和发布采用串行化或合理的版本乐观检查，避免两个构建抢占同一空槽。

## 10.3 可复现性的两种含义

**AI 创作可追溯：** 保存真实生成文件、模型、Prompt、输入和调用记录；不承诺重新请求 AI 得到逐像素相同结果。

**确定性编译可复现：** 同一素材哈希、配方、Profile、Compiler 和布局条件下，像素结果一致；若要求最终 PNG 字节和哈希完全一致，需控制编码器版本与 PNG 元数据。

## 10.4 最小备份和恢复

V0.1 必须有脚本级备份/恢复。数据库和文件要来自**同一个一致快照**，首期可在备份窗口暂停写入与垃圾清理。恢复到干净环境后，验证源纹理、配方和 Pack 均可读取，并能够**重新执行构建**，不能仅查看之前导出的 PNG。

# 十一、质量保证、预览可信度和验收证据

## 11.1 硬校验随产物实施

质量规则不能等到 Web UI 完成后才补：

- 源素材、配方、Tile IR 的合法性：由源与处理模块负责。
- Compiled Fragment、三源帧和目标格式：由 Compiler 负责。
- Layout Plan、图集尺寸、槽位和 Manifest 一致性：由 Pack/Atlas 模块负责。
- 文件引用、项目依赖版本、发布条件：由存储与构建模块负责。
- QA UI：复用前述规则，统一展示报告，**不承担唯一的结构验证责任**。

所有硬性错误阻止标记为有效的 MZ 交付。

## 11.2 视觉风险和人工美术验收

视觉风险提示可以覆盖：纹理接缝、内部四分之一图块连接、重复图案、色相/亮度突变、动画跳变/闪烁、波纹几乎无变化、岸线不自然。

不要把低接缝差异当成美术优质；纯色图可能很“无缝”，三帧相同的水面也不会闪烁，但均不代表目标效果成功。

自动视觉模型分析可辅助评价，不能替代确定性格式检查。首期“自动修复”仅承诺问题定位、有限确定性修复和重新生成选定组件；视觉内容改变需新 revision 与重新验收。

## 11.3 双预览与独立参考

创作预览检查源纹理/组件；交付预览**必须从实际的 PNG、Manifest、Target Profile**重新读取，并按目标的连接和动画规则显示。

预览与编译器可能共享错误，因此还须有与生产算法独立的编号/方向/拐角诊断素材，及经人工确认的草地—水面—岸线真实美术母版。

结构测试尽可能穷举 Profile 支持的合法形态及各动画状态；视觉测试用孤立格、直边、内外角、孔洞、单格宽通道、对角接触、大面积重复和实际池塘的代表场景。

## 11.4 明确四种验证状态

| 状态 | 解释 |
|---|---|
| STRUCTURAL_PASS | 工程结构自动校验通过 |
| VISUAL_CONFIRMED | 人工或明确指定流程确认视觉质量 |
| PROFILE_VERIFIED | 构建使用的 Target Profile 有实机测试基线 |
| ARTIFACT_MZ_TESTED | **这份具体产物**在指定 MZ 环境完成真实测试 |

使用已测试的 Profile **不能自动等同**具体文件 ARTIFACT_MZ_TESTED。未做实机测试标为 NOT_EXECUTED，不得写 PASS。

## 11.5 AI 质量评价

正式质量评测以**一套完整草地＋水面＋岸线 Pack**为成功单位，而不是只统计单张模型输出。需要统计所有尝试、不可用候选、模型错误、人工修复次数、用时、费用以及最终成功率。

步骤 09 用探索集确定配方和候选模型，并将正式评测阈值、重试和人工干预预算提交用户确认；步骤 10 用保留测试集验证，不允许看见失败后临时下调指标掩盖问题。

# 十二、系统架构与完整技术选型

## 12.1 技术栈

| 层 | 选型 |
|---|---|
| 前端 | React + Vite + TypeScript Strict |
| 地图/动画交付预览 | PixiJS |
| 后端 | NestJS + Express（默认适配）+ Node.js |
| ORM | Prisma（V0.0 固定已验证版本） |
| 本地数据库 | PostgreSQL（本地运行，不用买服务器） |
| 类型/HTTP 契约 | Zod、OpenAPI，明确可序列化边界 |
| 视觉模型 | WaveSpeed 官方 JS SDK 经 AI Gateway |
| 图像处理 | Sharp 等成熟库 + 可测试的确定性像素算法 |
| 资产 | 本地文件系统；未来 S3 兼容对象存储 |
| 任务 | 本地持久化任务执行；未来 Redis + BullMQ |
| 项目 | pnpm Workspaces Monorepo |
| 测试与 CI | Vitest、Playwright、类型检查、Lint、Build、图像/目标引擎回归 |

选择 NestJS 主要是模块约定、依赖注入和长期 AI Agent 维护的一致性，并非因为 HTTP 性能是最大瓶颈。真正图块处理、Compiler、领域语义应是**框架无关的 TypeScript 核心**，可以命令行独立执行和测试。

首期本地 PostgreSQL 增加少量环境准备成本，换取统一持久化基础；不代表未来可省略多租户、并发、账户数据迁移或计费一致性的开发。

## 12.2 API、领域与数据库分层

Zod 可以作为 HTTP 输入/输出契约单一来源，但不能把同一个 Zod Schema 强制同时充当 API DTO、领域模型、Prisma 数据表、快照和导出文件。各层有不同安全和持久化语义；采用明确、可测试的转换边界。

HTTP 数据应该可 JSON 序列化；Date、BigInt 等不应假设直接可以无损映射成 OpenAPI。不得把数据库实体连同本地路径、外部任务调试字段等直接暴露到前端。

## 12.3 最小工程闭环

V0.0 验证：

    React 发请求
        → NestJS 处理并执行契约校验
        → Prisma 写/读 PostgreSQL
        → 返回合法 API 响应
        → React 展示
        → 正式 build 后独立启动后端

同时验证 ESM/CJS、TS 包导出、Prisma Client 生成、开发/生产启动和单元测试。不能只凭 typecheck 通过就宣布技术栈可用。

## 12.4 计算任务边界

远程 AI 主要是异步 I/O 等待；图像编码及部分像素循环是本地 CPU 密集工作。根据实测使用异步 I/O、Worker 线程或本地子进程，避免阻塞 HTTP 事件循环。**模块化单体不要求所有任务都运行于同一个线程。**

## 12.5 推荐工程组织

    rpg-maker-maker/
      apps/
        web/            React + Vite + PixiJS
        api/            NestJS HTTP / orchestration
      packages/
        contracts/      HTTP contracts & types
        asset-core/     domain / recipe / version
        material-processing/
        mz-compiler/
        pack-assembly/
        validation/
        ai-gateway/
        persistence/
      tests/fixtures/   golden assets & MZ scenarios
      docs/
        plans/          本产品方案与执行计划
      AGENTS.md

具体 Package 数量由步骤 02 结合依赖边界确定，不应为抽象名词机械拆包。步骤 01 仅需小型独立原型与最小 Git/运行约束，无需提前创建完整目录树。

# 十三、Local-first 安全边界与未来 SaaS

## 13.1 本地 V1.0

React 与 NestJS 本地运行，PostgreSQL 使用本机服务或 Docker，本地文件保存素材。远程 WaveSpeed API 由后端调用，**不要求部署云服务器、Redis 或微服务**。

V1.0 的“非开发用户能完成工作流”指**在文档化的环境部署完成之后**，可以独立创作、预览、修复、导出并进入 MZ 使用。首期不承诺一键桌面安装器，也不开发自动更新系统；要提供统一启动入口、环境检查和易理解的错误提示。

## 13.2 没有登录也必须有基本安全

本地 API 默认仅绑定环回地址；明确 Host/Origin 和变更接口的防护策略，不能把 CORS 当成所有写接口的安全保证；校验上传真实格式、体积及解码后的像素数量；不允许用户输入任意服务端本地路径；密钥只在服务端，日志不得泄露。

使用外部模型时，用户应知道文本、参考图等必要数据会传给服务商；**模型名称 UI 隐藏不等于隐藏数据流向**。

## 13.3 未来线上服务的边界

未来架构可以演进：

    Web / CDN
        → NestJS API
        → PostgreSQL
        → Redis / BullMQ + image / AI workers
        → Object Storage
        → Provider API

届时需要新增身份、会话、Workspace、授权、并发隔离、服务安全、费用控制和线上数据迁移。这些是后续工作，不能声称本地 PostgreSQL 已经解决线上商业化。

## 13.4 商业化模块保持独立

成熟后按需增加：

- Identity：用户注册与 Google OAuth/OIDC 等。
- Workspace：用户及团队的资产归属/隔离。
- Metering：模型调用与用量统计。
- Billing / Ledger：Credits、余额扣减、退款与不可变账本。
- Payments：Stripe、微信支付、支付宝及回调/订单对账。
- Audit：关键操作与收费审计。

第三方支付与内部账户记账必须隔离，回调需要验签、幂等及交易核对；Redis 不是资金账本的权威来源。**当前版本只保留稳定资产/任务标识与可用调用记录，不提前实现任何收费模块。**

# 十四、全 AI 开发、逐步 Review 与变更治理

## 14.1 开发主线

V1.0 不按功能数量冲刺，而按风险和依赖推进：

    MZ 原生可行性与 Profile
      → 工程基础
      → 领域/像素与岸线配方
      → MZ Compiler
      → Pack/稳定槽位
      → 构建持久化 + Mock 恢复
      → 人工素材工作台与网页动画预览
      → WaveSpeed + Prompt 策略
      → AI 整套素材生产
      → 产品化与最终验收

对应 **10 个编号步骤**详见配套 [V1.0 开发计划](./02_V1_IMPLEMENTATION_PLAN.md)。

## 14.2 Review 门禁

每步都应由 Codex 提交**确定的受测 commit、关键构建文件哈希、Profile 版本、测试命令及结果、独立 Review 结果和必要的 MZ 实测证据**。由用户作最终步骤批准。**技术门禁和用户批准同时满足**才可进入下一步。

同一步可因修复缺陷修改以前步骤代码，但须回归相关能力；不得为了满足当前步骤擅自更改已经批准的 Profile、首期兼容承诺或产品范围。如需规格变更，提交独立影响说明由用户确认。

Review 结果只能绑定已测试的候选提交与产物。RC 后有实质性改动应按影响重新验证；未执行的独立审查或 MZ 测试必须如实记载。

## 14.3 AI Agent 工程规范

项目 AGENTS.md / Architecture Decisions 应记录：

- 哪个包拥有领域、像素、布局和供应商规则。
- 共享 API/Schema 的来源、允许的依赖方向。
- 核心数据与构建的不可变及迁移要求。
- 不改变默认 Prompt / 模型而无记录。
- 修改编译器与 Profile 时的回归和真实验收。
- 必要用例不得为让 CI 变绿而无依据删除或降低阈值。
- Reviewer 不得将自己生成的同一套测试结果当成独立依据。

不必机械为每个 getter 编写测试；测试应优先覆盖规则、边界、资源/金钱安全和失效恢复。

## 14.4 可复核证据

应持续维护简明需求映射：**V1.0 产品要求 → 开发步骤 → 自动/手工验证方式 → 提交与产物证据**。不要到最终发布才第一次核对需求。

必要时把以下状态分别标为 PASS、FAIL、NOT_EXECUTED、BLOCKED：编译结构、MZ 编辑器绘图、MZ 运行时动画、视觉确认、备份恢复、独立 Review。不能靠一句“已经 Review”推导出未执行测试通过。

# 十五、分阶段版本计划与退出条件

**这部分定义产品里程碑。具体每一步的 coding 和审批安排以十步计划为准。**

## 15.1 V0.0 — 引擎实验与技术基线

**目标：** 消除阻止原生 MZ 方案成立的关键不确定性，冻结可执行的工程契约。

工作流 A：Target Profile、A1/A2 槽位/容量、动画时基、Pixel Contract、诊断图集、真实美术母版、岸线方案、最小独立编译原型与原生 MZ 编辑器手绘地图/运行验证。

工作流 B：最小 TypeScript Monorepo、NestJS/React/Prisma/PostgreSQL 请求链路、生产构建启动、CI/AGENTS.md、Asset/Fragment/Layout/发布和 AI Gateway/任务状态契约；不提前搭建完整后台或接入付费 AI。

**退出条件：** 所有已识别、会阻止 V0.1 开始的前置假设已验证并关闭；草地/水面/岸线能在原生 MZ 中正确组合及播放；未解决的后续风险有分配阶段。**不要求证明所有未来风险都不存在**，也不要求真实 AI 成功率已经达标。

## 15.2 V0.1 — 确定性素材引擎与可用的人工工作流

实现 Asset/Transition/Animation IR、Pixel Processing、单素材 A1/A2 Compiler、Pack Layout、Atlas Renderer、稳定槽位/退役、Manifest、不可变项目快照、PostgreSQL/文件一致性发布、备份/恢复、Mock Provider 持久化任务状态、实际产物预览、人工纹理导入与基础 Web Studio、结构 QA 报告。

**退出条件：** 不接 AI 就能从合格人工素材生产真实 MZ Pack；旧地图更新仍正确；构建失败可恢复；Mock 的未知提交/恢复/归档/迟到结果测试通过；网页可以播放编译后的普通水面动画。硬校验从源、编译、布局到发布分别生效，不等到前端才实现。

## 15.3 V0.2 — WaveSpeed AI 创作 MVP

接入真实 WaveSpeed SDK，分别打通文生图和参考图编辑上传/归档；内置主 Prompt 模板和可选用户辅助提示词；用受约束的草地、水纹、岸线配方产出完整素材包；支持候选、局部重生成、模型配置冻结与费用记录。

**退出条件：** 文本入口及参考图入口**分别**可以生产整套草地/水面/岸线 Pack 并通过实际 MZ 使用验证。积累失败/重试/人工修复数据，在正式保留集测试前提出质量阈值与预算，由用户批准。

## 15.4 V0.3 — 质量、可靠性与产品体验

完善素材 Studio、两种预览、视觉风险、受控修复、项目历史、生成任务恢复、安装说明、本地安全与环境检查。固定与保留评测集验证实际质量和成本。

**退出条件：** 在安装好依赖的环境中，非开发用户可独立完成创作、候选、修复、预览、导出、MZ 数据库注册与绘制；错误可定位，失败保护和回归有效。

## 15.5 V1.0 — 正式候选与发布

在同一最终步骤中区分：产品化完成 → 冻结 RC（代码/依赖/Profile/模型与 Prompt 配置、Build 哈希、质量门槛）→ 全量自动化/实机/独立 Review → 用户审批。

**发布门槛：** 全部首期能力真实可用；原生 MZ 无插件使用；图块和动画符合 Profile；已有地图在正常更新后保持声明的槽位语义；数据恢复通过；质量/成本达到预先冻结的阈值；不存在阻断性缺陷；记录证据和未执行事项。

当前文档更新不视为任何实现步骤完成。每一步均应等待用户的明确批准。

# 十六、未来扩展路线（不属于 V1.0）

**V1.x 新地形**：道路、雪/沙/泥地、河流、瀑布、岩浆、崖壁、墙体、建筑和更多材质过渡；按需新增 MZ 其他 A1 子类和 A3/A4/A5/B-E 编译规则。每新增类型须独立 Profile/验证，不能推断旧素材能够无损转为所有未来格式。

**Enhanced MZ 动画**：通过可选 MZ JS 插件/运行时适配支持 N 帧、非往返循环、独立速度等；尽量复用编辑器已有地图形状和稳定图块身份，但编辑器是否显示高级动画必须单独验证。它不应成为智能笔刷开发的强制依赖。

**SaaS**：云端 API/Workers、S3 对象存储、Redis/BullMQ、登录、支付、计费、审计等按需加入，和新地形扩展可以独立推进。

**V2.0 智能笔刷**：建立地图文档与语义笔刷，利用已有材质身份、Transition 依赖和稳定槽位表达道路、水深、山体层级、树木密度、地形自动过渡以及 MZ 地图数据导出。

**动态环境**：风场、每棵树独立摇摆、水面 Shader、落雪/樱花/粒子等是独立运行时系统，不由首期 Autotile Compiler 直接承担。

# 十七、验收矩阵、关键风险和优先级

## 17.1 V1.0 核心验收矩阵

| 产品要求 | 实施归属（十步计划） | 证明方式 |
|---|---|---|
| MZ 原生草地/水面/岸线 | 01、03–05 | 独立诊断图、编辑器手绘、运行录像或记录 |
| A1/A2 编译和三源帧时基 | 01、04、07 | 完整形态/帧状态测试及 MZ 实机 |
| 多素材 Pack 和槽位退役 | 05–06 | 更新既有地图验证、退役与冲突测试 |
| 原始像素质量及固定过渡 | 03、09 | 像素回归、视觉审查和生成评测 |
| 项目快照与备份恢复 | 06 | 干净环境恢复后重新编译 |
| 不可变发布/旧构建不覆盖新构建 | 06 | 注入故障、反向完成/并发竞态测试 |
| Mock 任务提交未知/恢复 | 02、06 | 无付费模型的故障模拟 |
| WaveSpeed 文本与参考图编辑 | 08–09 | 受控真实 API、结果本地归档 |
| 平台主 Prompt/用户可选补充 | 08–09 | 空补充、冲突、模板版本冻结测试 |
| 编译图集浏览器动画预览 | 07、10 | 从实际 A1/A2 文件重建并播放 |
| 视觉 QA 与局部重生成 | 07、09–10 | 问题定位/保护像素/重建与复测 |
| 最终质量、成本与可用性 | 09–10 | 预先冻结阈值，保留集评测与最终 Review |

具体证据由十步计划中的每步报告持续补齐，不能等 V1.0 才首次确认功能存在。

## 17.2 主要风险与原则

**原生 MZ 岸线不能按设想绘制：** V0.0 应报告失败证据和候选方案，不能直接绕过验证开发 MZ 插件来扩充首期。

**AI 美术结果不稳定：** 通过共享配方、候选评估、受约束生成和可控重试来改进；不得把无限重试算成“稳定高成功率”。

**图像处理损坏像素风：** Pixel Contract、独立样例和明确缩放/Alpha 合成规则。

**预览自证正确：** 从实际最终图集预览 + 独立诊断资产 + 原生 MZ 验收。

**旧地图因更新槽位损坏：** 已用槽位稳定、退役保留、旧地图替换实测。

**供应商重复调用导致花费：** 任务状态、SUBMISSION_UNKNOWN、重试与并发上限、预算控制。

**数据库引用不存在的文件：** 先保存不可变文件，后短事务发布引用并条件切换，失败保护。

**AI Agent 架构漂移：** 模块契约、依赖自动检查、固定回归、独立 Review、与每次提交绑定的证据。

## 17.3 不可降级的底线及优化排序

**不可降级的基础门槛：** 工程正确性、用户素材/项目数据完整性、基础安全、受控外部付费调用、构建与发布一致性，以及验收结论真实。

在上述门槛满足之后，优化优先级为：实际可用性 → 稳定性与素材质量 → 可维护性与合理扩展性 → 功能数量 → 开发速度。

不允许以“更漂亮的水面”为理由接受项目文件被破坏，也不允许以提高成功率为理由接受不可控的重复付费请求。

# 二十、最终实施结论

**V0.5 的范围和技术路线已经通过方案级 Review：可以按照配套十步开发计划进入 V0.0。**

本版交付的是：一个本地运行、使用内置主 Prompt 与可选辅助 Prompt、由 WaveSpeed 生成源视觉素材、由确定性引擎编译并组装草地/动态水面/固定岸线、可以在浏览器直接播放最终 Animated Autotile、能够保存/恢复/检测/下载、并经过真实 MZ 约束验证的完整 V1.0 工具。

不应在第一版提前实现收费、认证、SaaS、智能笔刷和增强动画插件。未来扩展沿着领域模型、Provider、Compiler、Pack 与运行时能力分层推进。

**开发治理最终原则：** 每个步骤先满足必要技术验收，再由用户明确 Review 批准；不可跳步。V0.0 允许发现尚未解决的风险，但必须记录并关闭所有阻止 V0.1 开始的已知前置问题。V1.0 只能在完整的测试、质量证据、独立 Review 和用户批准后宣布完成。

**文档批准不等于代码或 MZ 实机测试已通过。修改本文件本身也不代表已开始步骤 01。**
